From ChromaDB to S3 Vectors — What I Learned About How Embeddings Actually Work

Moving a RAG system's vector store taught me more about embeddings than building it did.

EP
Eshwar Prasad YaddanapudiJan 1, 2026 · 12 min read · Engineering Lab
Mockup text. The real article content is imported from the blog.

Every RAG tutorial starts with a vector database and ends with a demo. Very few tell you what happens when you need to move one. When I migrated from ChromaDB to S3 Vectors, the assumptions I had about embeddings broke one by one.

Why move at all

ChromaDB was perfect for prototyping. But a local store doesn't fit a system that needs to scale to zero and survive restarts. S3 Vectors promised durable, cheap storage with similarity search built in.

Key idea: an embedding is only meaningful next to other embeddings from the same model. Change the model, and every stored vector becomes noise.

The migration script

The first version was a straight copy. It worked, and it was wrong. Here's the shape of the fix:

migrate.ts
const vectors = await chroma.get({ include: ["embeddings", "metadatas"] });

// Re-embed instead of copying: same model, same dimensions
for (const doc of vectors.documents) {
  const embedding = await embed(doc, { model: MODEL_ID });
  await s3v.putVectors({ index, vectors: [{ key: doc.id, data: embedding }] });
}

What I actually learned

Dimensions, distance metrics and normalization aren't configuration details. They're part of the data. I now store the model ID next to every vector, and I treat cosine versus euclidean as a schema decision, not a tuning knob.

What comes next

The next step is agentic retrieval, where the system decides when to search, not just what to search for. I wrote about that in From RAG to Agentic RAG.
